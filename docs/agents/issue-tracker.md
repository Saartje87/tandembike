# Issue tracker: Local Tandembike app (MCP)

This repository's Tickets live in the local Tandembike app, in the Project named `Tandembike` (id 3, so its pages are under `http://localhost:4747/project/3`): use it for all work on this codebase, and do not create a second one. Ticket summaries carry no Project id; `get_ticket` returns it as `projectId`. Reach it through its MCP server at `http://localhost:4747/api/mcp` with an MCP-capable client; the app must be running. Use its tools, not `gh`, `glab` or `.scratch/` files, even where a skill describes another tracker. The server's instructions and tool descriptions explain how the tracker works: the folder default, `start_work` to begin, `finish_work` or `abandon_work` to end, `file_tickets` for new work, native Blockers and acceptance criteria, and each tool's rules (ADR 0014). This document adds only this repository's process on top of them. One Ticket's run, from claim through merge, follows [`start-run.md`](start-run.md); this document holds the rest.

## When the MCP tools change

A change to the MCP server in `src/mcp/` reaches the running app on save under `npm run dev`, and only after `npm run build` and a restart under `npm run start`. Once it has, ask the User to start a new session to pick up the new tool descriptions and instructions. Reconnecting with `/mcp` in Claude Code is not enough: it reconnects the server, but tool descriptions this session has already loaded stay as they were. Until the new session, treat your loaded tool descriptions as out of date.

## The Board and Ticket lists

Board Lanes (Intake, Queued, In progress, Your work, Done) and the In progress sections (Action needed, Running, Review) are derived in the UI and stay out of the MCP tools (ADR 0023): no tool returns or filters by a Lane. Lane order is the User's to set in the UI; ask them rather than reordering.

To see a Project's structure, start from the `find_tickets` summaries: each row has `epicNumber`, the Epic the Ticket is a child of, or `null`. When you need more than a summary, such as each Ticket's criteria or Claim, pass `detail: "full"` with `description: false`. A full list with descriptions can grow too big for the client to return.

## Worktrees for parallel runs

When Tandembike starts a Start run with Parallel runs on, it makes the run's worktree itself, under `~/.tandembike/worktrees/`, detached at the up-to-date default branch, and starts the run inside it. Such a run is already in its worktree: it creates its branch there, makes no other worktree, enters none, and does not remove its own, since Tandembike does. The rest of this section is the recipe for the Agent runs Tandembike does not start in a worktree, such as terminal sessions and subagents that share the checkout with another run.

Setup takes three turns: create, enter, and at the end tear down.

- **Where.** `.claude/worktrees/<slug>/` inside the repository, which is git-ignored. Create it before you change any file, and stay inside it.
- **Create it.** From the main checkout, one command fetches, creates the worktree off `main` on the branch `AGENTS.md` names, and compares its lockfile with the main checkout's:

  ```sh
  git fetch origin main && git worktree add --no-track -b ticket-<number>-<slug> .claude/worktrees/<slug> origin/main && git diff --no-index --stat package-lock.json .claude/worktrees/<slug>/package-lock.json
  ```

  Each part matches the committed allowlist in `.claude/settings.json`, so it runs without a permission prompt. The last part prints nothing when the lockfiles match. When they differ it prints a diffstat and exits 1: that is input for "Prepare it", not a failed setup. Keep `--no-track` whenever the start point is a remote branch: tracking writes the shared `.git/config`, and runs that start at the same moment collide on its lock. You set the upstream later with `git push -u`. `EnterWorktree` with a `name` also creates a worktree there, but on a branch it names itself, so use the command above for a Ticket branch.
- **Recover.** If `git worktree add` fails with `could not lock config file .git/config`, it may have created the branch but not the worktree. Then attach the existing branch without `-b`, and compare the lockfiles as the create command would have: `git worktree add .claude/worktrees/<slug> ticket-<number>-<slug> && git diff --no-index --stat package-lock.json .claude/worktrees/<slug>/package-lock.json`.
- **Enter it.** In the main session, once the worktree exists, call `EnterWorktree` with its `path`; it accepts any worktree under `.claude/worktrees/` that `git worktree list` shows. From then on every command runs inside it, so write commands bare (`npm run check`, `git status`). A `cd <worktree> && …` prefix does not match the committed allowlist in `.claude/settings.json`, so each one stops for a permission prompt.
- **In a subagent, work by absolute path.** `EnterWorktree` works in the main session only: a subagent starts in its parent's working directory and cannot switch, so `EnterWorktree` refuses it with "current working directory is the repository root", whatever `path` it gets, and a `cd` does not carry to its next command. Don't call it. Read and edit files by their absolute path under the worktree, which the allowlist covers. Run commands against the worktree without `cd`: `git -C <worktree> status`, `git -C <worktree> commit …`, `npm --prefix <worktree> run check`. These forms do not match the allowlist either, since its entries start `git status` or `npm run check`, so each one may stop for a permission prompt like a `cd` prefix; they still beat `cd`, since they keep the command one plain call.
- **Prepare it.** The app keeps its database in the folder (`data/`), so a fresh worktree starts with an empty one and needs no env file. Install only when the create command printed a diffstat, when your work changes `package-lock.json`, or when the run will serve the app (`npm run dev`, a browser check). Then run `npm ci --prefer-offline --no-audit --no-fund --ignore-scripts && npm rebuild better-sqlite3` inside the worktree; otherwise skip both. Skipping is safe because Node finds packages by walking up the folder tree: a worktree under `.claude/worktrees/` with no `node_modules` of its own uses the main checkout's, which match its lockfile, and `npm run check` and the pre-commit hook run on them. That holds only for a worktree inside the main checkout; one outside it, like `browser-checks.md`'s, finds no `node_modules` above it unless one was installed there. Serving needs the install even inside the repository, because Turbopack will not resolve packages outside the folder it serves. For the same reason, do not symlink `node_modules` (steps 2–3 of `browser-checks.md`). The rebuild prints `npm warn rebuild 6 packages have install scripts not yet covered by allowScripts` (4 on a later rebuild). The warning is expected; ignore it. On macOS the packages are `better-sqlite3`, `fsevents` (macOS only), `@swc/core` and three versions of `esbuild`, and the repository has no `allowScripts` list. The recipe skips install scripts on purpose and rebuilds only `better-sqlite3`, the native module the app needs. `esbuild` and `@swc/core` take their binaries from platform packages, and `fsevents` ships prebuilt. In npm 11.17 the field is advisory: an unlisted script still runs, with this notice, and fails only under `strict-allow-scripts`, which is off. Do not run `npm approve-scripts` or `npm deny-scripts`, and do not add `allowScripts` to `package.json` for it.
- **Ports.** Port 4747 belongs to the User's running app, and your MCP tools reach Tickets through it, so never run `npm run dev` or `npm run start` in a worktree without a port: both default to 4747. To serve the app, run `npm run dev -- -p <port>` on a free port, such as 3100 and up; each parallel run takes its own. A browser check's helper finds that port through `BROWSER_CHECK_PORT` (default 3100), so set it to the same port rather than editing the helper (`browser-checks.md`). Use that throwaway server and its own `data/` for anything that creates or deletes Tickets, as `browser-checks.md` requires. It shares `~/.tandembike/worktrees/` with the User's app but only ever removes the worktrees its own Conversations made there, so it leaves the app's live run worktrees alone. `npm run check` needs no server. Runs that this throwaway server starts reach Tickets through port 4747 unless you set `TANDEMBIKE_MCP_URL=http://localhost:<port>/api/mcp` when you start it. To check such a run, set its throwaway Project's repository path to your own worktree, so the run works on your branch. Claude Code then writes the run's log in `~/.claude/projects/<folder>/`, where the folder is named after the run's final working directory with `/` and `.` as `-`: next to your own session's, unless the run worked in a nested worktree (it entered one under `.claude/worktrees/`), in which case the folder's name is longer. So search every folder whose name starts with your worktree's, by the run's first prompt: `grep -l 'Triage T1' ~/.claude/projects/<worktree path with / and . as ->*/*.jsonl`. Don't take the newest file: that is usually your own session.
- **Clean up.** Remove the worktree as the last step of your work: after `finish_work` once the PR is merged, or after `abandon_work` or `open_pr` with `handOff: true` when the PR stays open. A terminal session or subagent gets no prompt to keep or remove a worktree it made with `git worktree add` when it ends, and nothing else removes it. Remove it yourself, and tell the User you did, not that they will be asked. A worktree Tandembike made for your Conversation is not yours to remove. Stop any server you started. If you entered an existing worktree with `EnterWorktree` and its `path`, leave it with `ExitWorktree` `action: "keep"`, which returns you to the main checkout, then from there tear it down in one command: `git worktree remove .claude/worktrees/<slug> && git worktree prune`. If `EnterWorktree` made the worktree from a `name`, `ExitWorktree` `action: "remove"` removes it in one step but deletes its local branch too, so push the branch before you call it. If removal refuses because of uncommitted files, commit or discard them first; do not use `--force` on work you have not pushed. Leave the pushed branch on `origin`: it is the PR's.

### Migrations in parallel runs

This applies to every parallel run, including those Tandembike starts in a worktree. `npm run db:generate` (`drizzle-kit generate`) numbers a migration one past the last in `src/db/migrations/meta/_journal.json`, so two branches that each add one both take the same number. Each writes its own `NNNN_<name>.sql`, `meta/NNNN_snapshot.json` and journal entry. `src/db/migration-files.test.ts` fails on a duplicate number, a gap, or a migration without its snapshot or journal entry, including when git merged the files without a conflict.

- **Generate last.** Change `src/db/schema.ts` first. Then merge the latest base branch (`main`, or the Epic's branch for a subagent building part of an Epic), and generate the migration as the last step before you report or open the PR.
- **Regenerate on a collision.** When your branch lands second and its number is taken, never merge snapshots or the journal by hand. Instead:
  1. Fetch the base and merge it: `git fetch origin <base> && git merge --no-commit origin/<base>`. It may stop on conflicts in `meta/`; the next step resolves them.
  2. Replace the whole `meta/` folder with the base's, which drops your snapshots and journal entries, even ones whose number the base lacks: `git rm -rq src/db/migrations/meta/ && git checkout origin/<base> -- src/db/migrations/meta/`.
  3. Delete each `.sql` file your branch added: `git rm src/db/migrations/<NNNN>_<name>.sql`.
  4. Regenerate them as one new migration, numbered after the base's, with `npm run db:generate -- --name <name>`.
  5. Run `npx biome format --write src/db/migrations/meta/`, because Biome's format check rejects drizzle-kit's snapshots.
  6. Compare the new SQL with your original: `git show <your branch>:src/db/migrations/<NNNN>_<name>.sql | diff - src/db/migrations/<new NNNN>_<name>.sql` prints nothing when they match (with several originals, compare their concatenation). Then run `npx vitest run src/db/migration-files.test.ts`, and commit the merge.
- **Merging a sibling branch.** Whoever merges a subagent's branch into the Epic's branch runs the same test after each merge, and has a failing branch regenerated with this recipe.

## Working an Epic

An Epic is handed off, worked and delivered as one unit:

1. `start_work` the Epic once. It claims the Epic and returns its children with their Statuses and Blockers and the next child to work.
2. Leave the children unclaimed: the Epic's Claim covers them.
3. Work the children in Blocker order on one branch named after the Epic, `ticket-<epic number>-<slug>`: next is a `Todo` child whose Blockers are Done, archived, or children already started on this branch (`In progress`); the bundle's `nextChild` names it. `start_work` each child as you start it: under your Epic Claim it moves the child to `In progress`. While the Epic is claimed an `In progress` sibling counts as a resolved Blocker everywhere (`start_work`, the `blocked` flag and filter, the Board), but a `Todo` sibling, or a child once the Epic's Claim is released, still blocks, and a Ticket outside the Epic stays blocked until the child is Done or archived. Check off its acceptance criteria with `check_criterion` as you verify them, and commit it on its own, naming it (`T42`).
4. Open one PR for the whole Epic, named after it, and add its URL to the Epic with `open_pr`, not to its children. Then merge it or hand it off with `open_pr` and `handOff: true` as the Epic's `start_work` `merge` says, by "The Claim, through merge" in `start-run.md`; a later run working on an open PR calls `start_work` on the Epic again.
5. Once the PR is merged with CI green, whoever that rule names calls `finish_work` on the Epic: the run itself with `merge: "auto"`, or the run the User's Approve merge resumes or starts. It refuses while the Epic or an unarchived child has an unchecked acceptance criterion, unless given an `override` reason. To see which, read each child's `uncheckedCriteria` in the Epic's `children`, or every child's criteria at once with `find_tickets({ epicNumber, detail: "full", description: false })`. In one transaction it completes every unarchived child, removes the Epic's own triage state label and releases its Claim; the Epic reaches `Done` with its children. Its category labels (`bug`, `enhancement`) and `wontfix` stay. This is the Epic case of the completion rule in `triage-labels.md`, and what the User's **Merged** button does.
6. A terminal session or subagent in a worktree of its own removes it last, after `finish_work` on the Epic or after handing the Epic off, by "Clean up" in "Worktrees for parallel runs".

## Feedback as Tickets

The steps for filing friction as Tickets are in "Feedback as Tickets" in [`start-run.md`](start-run.md).

## Triage and Blockers

Record triage roles as labels: one category label (`bug` or `enhancement`) and one state label; the allowed state roles are listed in `triage-labels.md`. When moving a Ticket to a new triage state, swap the state labels in one `update_ticket` call with `removeLabels` and `addLabels` (plus any other field changes, such as the description). A Triage run of the default Playbook proposes with `propose_triage` instead; the User's Approve applies the labels (see `triage-labels.md`). Otherwise post triage notes as a comment with `add_note`, starting with `> *This was generated by AI during triage.*`; leave the description alone unless the triage changes what the Ticket asks for. Older Tickets may still have a `## Triage notes` section in the description; leave it in place. Older Tickets may still have a `Blocked by: #<number>` line in the description; when you touch one, add those Blockers with `update_ticket` and `addBlockers` and delete the line, preserving the rest of the description. Represent `wontfix` with the `wontfix` label and keep the Ticket active.

## Publishing a spec

A spec is always an Epic in Tandembike, whatever its size, so that its build Tickets hang off it and "Working an Epic" applies. Unless it fills an existing Epic, a placeholder being triaged or named by the User or a named Epic that already has children (below), `/to-spec` publishes it with `file_tickets` (`type: "Epic"`) in the work's Project, with the spec as its description and the `ready-for-agent` label; `/to-tickets` then creates its children in one `file_tickets` call with its `epicNumber` and their Blockers in `blockedByPositions`, each labelled `ready-for-agent`. A spec of one Ticket's worth is an Epic with one child.

Check what changed in the target Project before you publish, since a spec session can run long while other sessions publish or change the work it builds on:

- **When.** Right before `/to-spec` publishes the spec or fills an existing Epic, and again right before `/to-tickets` creates or reconciles its Tickets. The session starts when you first read the tracker in it, since everything before that is already in what you read; note that time then, in UTC (`date -u +%Y-%m-%dT%H:%M:%SZ`).
- **The call.** List the target Project's open Epics changed since then: `find_tickets` with `projectName`, `type: "Epic"`, `status: ["Todo", "In progress"]` and `changedSince` set to that time, plus `cycleId` when the work is planned into a Cycle.
- **What to read.** Read each Epic that comes back with `get_ticket`, except the spec's own Epic.
- **What to do.** If one removes, renames or rebuilds something the spec relies on, stop and tell the User before publishing. Otherwise go ahead.

When the spec removes or moves a UI surface (a page, a panel, a card, a menu, a drawer section), check that its actions survive before you publish. Removing a surface without this check is how the five-Lane Board's Merged and Back to Todo were lost (T1151):

- **List the actions.** Read the surface's code and write down every action it offers: buttons, menu items, links, keyboard shortcuts, drag targets.
- **Give each a home.** For each action, name where it lives afterwards: another surface that already has it, a build Ticket in this breakdown that adds it, or an explicit decision in the spec's Out of Scope to drop it. Put the list in the spec's Implementation Decisions, and give the Ticket that removes the surface a criterion that each action has its home. An action with none: stop and ask the User.
- **Re-triage what targets it.** Search with `find_tickets` for open Tickets that change the surface (its name, its component, its actions). Each one that comes back is built for something that will be gone: comment on it naming the spec's Epic and what changes, and swap its triage state label for `needs-triage` with `update_ticket`, so `/triage` reworks it against the new home. Tell the User which you flagged.

When the spec refines an idea Ticket, for example one grilled in `/triage`:

1. Stop triaging it, tell the User, and continue in the same session with `/to-spec`, then `/to-tickets`.
2. Publish the Epic and its children in one `file_tickets` call, with the idea Ticket as the `originNumber` of the Epic's own entry, not the batch's, so only the Epic is split from it. The idea Ticket itself cannot become the Epic: a Ticket's type is fixed at creation.
3. Comment `Refined into Epic T<number>` on the idea Ticket, remove its triage state label, and archive it with `update_ticket` and `archived: true`. Keep it out of the Epic: an Epic's Status follows its children, so a finished idea child would show the Epic `In progress` before any work starts.

When the Ticket being triaged is an Epic with no children, or the User names an existing Epic with no children while running `/to-spec`, that Epic is a placeholder and becomes the spec itself. Examples are a follow-up an earlier spec filed as an Epic, or a roadmap phase's Epic. Replace its description with the spec and give it `ready-for-agent` with `update_ticket`, removing any other triage state label in the same call; a placeholder may carry none. It keeps its number, its other labels and its Origin. `/to-tickets` then creates its children under it with its `epicNumber`. Do not publish a new Epic, and archive or replace nothing. An Epic is a placeholder only when it is being triaged or the User names it, not by its labels; without either, `/to-spec` publishes a new Epic as above.

When the User names an existing Epic that already has children while running `/to-spec`, for example after a grilling session filed its children before the spec was written, it becomes the spec the same way: replace its description with the spec and give it `ready-for-agent`, and it keeps its number, its other labels, its Origin and its children. Do not publish a new Epic: that duplicates the Epic and orphans its children (T1358). `/to-tickets` on that Epic then **reconciles** its children against the spec instead of filing a second set. Read each unarchived child with `get_ticket`, then:

- **Keep** a child the spec covers as it is.
- **Reword** a Todo child where the spec sharpens it: its title, description or `acceptanceCriteria`, with `update_ticket`. A child that is In progress or Done and differs from the spec is flagged instead.
- **Add** each slice the spec needs that no child covers: `file_tickets` with the Epic's `epicNumber`, and `addBlockers` with `update_ticket` for Blockers between new and existing children, in either direction.
- **Flag** a child the spec does not cover, or does not match and cannot be reworded: comment on it with `add_note`, naming the spec's Epic and what the spec leaves out, and leave it as it is. The User decides whether it goes; the run never archives it. List the flagged children to the User at the end.

Show the reconciled breakdown, marked keep, reword, add or flag, when you quiz the User, and change nothing until they approve it.

When the spec is feedback on an Epic that is already built or in review, such as follow-up requests after its PR, publish a new Epic with the existing Epic as its `originNumber`, and leave the existing Epic unchanged: no comment, no archive. Its new branch starts from the existing Epic's branch, and its PR targets that branch while the earlier PR is open.

## Acceptance criteria

When a skill's template (such as a `to-tickets` issue or a `triage` agent brief) has an acceptance-criteria checklist, pass those items as `acceptanceCriteria` on `file_tickets` or `update_ticket` and leave that section out of the description or comment. Confirm with `get_ticket` that they were stored.

A criterion that names a doc, a section or a `GLOSSARY.md` entry says "add" when it does not exist yet and "update" when it does, so the implementer need not guess. Check that it exists before you write the criterion.

Older Tickets may still carry an acceptance-criteria checklist in the description; when you touch one, move those items into `acceptanceCriteria` (keeping their checked state) and delete the checklist, preserving the rest of the description.

## When a skill says “publish to the issue tracker”

Create one Ticket per approved work item in the selected Project, using the MCP tools, with its acceptance criteria in `acceptanceCriteria`. Create them in one `file_tickets` call, in dependency order, with each dependency in `blockedByPositions`, or in `blockedByNumbers` when it is an existing Ticket; for more than 50 items, use further calls. To name a sibling in a title, description or criterion, write `{{T:n}}` (n its position in the call, from 0) instead of guessing its number.

When the items are split from an existing Ticket that is not an Epic, such as a spec, pass that Ticket as `originNumber` so they form its Origin group (ADR 0015). Then finish the split Ticket with `finish_work`, which moves it to `Done` and removes its triage state label (with an `override` reason if its criteria are left to the split-off Tickets), and do not archive it: its drawer lists the split-off Tickets and stays on the Board as the group's view. Each split-off Ticket is then worked on its own, by `start-run.md`.
