# Triage Labels

The skills speak in terms of five canonical triage state roles. Each is a native Ticket label of the same name. A Ticket carries exactly one state label at a time, so move it between states with one `update_ticket` call that names the old label in `removeLabels` and the new one in `addLabels`, for example `removeLabels: ["needs-triage"], addLabels: ["ready-for-agent"]`. `update_ticket` also takes an array of Ticket numbers (up to 50) to move several the same way at once.

| Canonical role    | Label             | Meaning                                      |
| ----------------- | ----------------- | -------------------------------------------- |
| `needs-triage`    | `needs-triage`    | Maintainer needs to evaluate this Ticket     |
| `needs-info`      | `needs-info`      | Waiting on the reporter for more information |
| `ready-for-agent` | `ready-for-agent` | Fully specified, ready for an agent          |
| `ready-for-human` | `ready-for-human` | Requires human implementation                |
| `wontfix`         | `wontfix`         | Will not be actioned                         |

Source labels (`from:tandembike`, `from:agent-run`) say where a filed Ticket came from: Blocks friction or an Agent run; they sit beside the state and category labels and change neither. A run may file at most 3 Tickets with a source label, and `file_tickets` refuses a near-duplicate title of a live one (neither Done nor archived). See "Feedback as Tickets" in `start-run.md`.

Triage category roles are the labels `bug` and `enhancement`. Find Tickets in a role with `find_tickets` and its `labels` filter, for example `labels: ["ready-for-agent"]`.

A Triage run ends with `propose_triage` (a category, a state, reasoning, optional criteria): it posts the reasoning as the triage comment and waits for the User's Approve, which sets the labels. This repository's own `/triage` override still posts with `add_note` and labels directly. Otherwise, post triage notes as a comment with `add_note`, not in the description. Start each with `> *This was generated by AI during triage.*`. Older Tickets may still have a `## Triage notes` section in the description; leave it in place.

Older Tickets may still carry `Triage category:` and `Triage state:` lines in their description. When you triage one, move those values to labels and delete the lines.

Finish a Ticket or an Epic with `finish_work`, the completion rule's one implementation (the Tickets module's `completeTicket`, which the User's **Merged** button on the Board also uses), and the one way an Agent moves work to `Done`, with a PR or without one (a split spec, `ready-for-human` work, research). It sets the Ticket's Status to `Done`, removes its active triage state label (`needs-triage`, `needs-info`, `ready-for-agent`, or `ready-for-human`) and releases its Claim. Category labels such as `bug` and `enhancement` stay, and so does `wontfix`. For an Epic, whose Status follows its children and cannot be set, it completes every unarchived child the same way and removes the Epic's own state label, in one transaction. See step 5 of "Working an Epic" in `issue-tracker.md`.

It refuses while any acceptance criterion is unchecked: the Ticket's own or, for an Epic, the Epic's and every unarchived child's; the refusal names each with its Ticket. A criterion you deliberately leave unmet: pass `finish_work` an `override` reason, which it posts as your comment naming the unchecked criteria. The Merged button is never refused: it lists the unchecked criteria and completes once the User confirms, recording that as the User's comment (ADR 0043). It checks nothing on GitHub: when there is a PR, call it only once the PR is merged with CI green.

Setting `Done` with `update_ticket` is for the User's own edits: it checks no criteria and leaves the labels as they are.
