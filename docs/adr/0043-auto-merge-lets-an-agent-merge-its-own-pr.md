# Auto-merge lets an Agent merge its own PR

Decided on 2026-11-09 (T1283). Amends [ADR 0038](0038-the-user-approves-each-merge.md): with a Project's **Auto-merge** on, the run that opened a PR merges it, so the Merge gate applies only when the setting is off or the run cannot meet the merge conditions. It also replaces ADR 0038's amendment for this repository (T1282): Tandembike's own self-merge becomes the Tandembike Project's Auto-merge being on, not an instructions override of the Playbook. It makes the completion rule stricter: `finish_work` checks the acceptance criteria.

Autopilot dispatches a Cycle's ready work, but every Start run stopped at the Merge gate, so a Cycle never finished without the User. The rules for reaching Done were spread out and contradicted each other: ADR 0038, the GLOSSARY and the Playbook said a Start run never merges, while this repository's `AGENTS.md` and `docs/agents/start-run.md` said it does. And `finish_work` checked nothing, so an Agent could finish a Ticket whose acceptance criteria were unchecked.

## Decision

- **A Project setting.** `autoMerge` is a Project agent setting beside `autopilot`, `parallelRuns` and `spendCeilingUsd`, off by default, so existing Projects keep the Merge gate. Only the User sets it, on the Project's agent settings through a Server Action, and it is not part of the Project the MCP tools show (ADR 0019, ADR 0030), so no Agent can turn it on. It does not depend on Autopilot: either can be on without the other.
- **One rule for every Agent run.** `start_work` returns `merge: "auto" | "approve"`, read from the Ticket's Project, beside `checkCommand`. It is the only way an Agent learns the setting, and it applies to every run in the Project: a Start the User pressed, one Autopilot dispatched, and a terminal session. The Playbook's `implement` and `implement-epic`, and a repository's own docs, follow it instead of stating a mode in prose.
- **The merge conditions.** With `merge: "auto"` the run merges its PR only when the Check command passes, its own review has no unresolved findings, every acceptance criterion is checked (or a comment says why not) and the PR's checks are green. It merges by the same steps an approved merge uses (the `merge` skill's): wait for the checks, rebase and push when the branch is behind, merge with the host CLI, then `finish_work`. It never pushes to the default branch.
- **The fall-back is the Merge gate.** When a condition fails, the run comments why with `add_note` and hands off with `open_pr` and `handOff: true`, as with Auto-merge off. The Ticket waits in Review, or Action needed, for Approve merge or Merged, which both keep working with Auto-merge on.
- **Only later runs.** The mode is read when `start_work` takes the Claim and is kept on it. Turning the switch on or off changes only runs whose `start_work` comes after it: Tickets already in Review stay at the gate, and nothing merges a batch of PRs.
- **Spend.** An auto-merge is part of its Start run, so its cost counts against the Spend ceiling and the Machine ceiling with the rest of the run, with no Run outcome of its own. ADR 0038's `merge` outcome, and its subtraction from Autopilot's spend, stay for merges the User approved.
- **A notice.** Completing a Ticket or Epic through an auto-merge (its Claim's mode is `auto`, it has a PR reference and an Agent calls `finish_work`) records an `autoMerged` Activity change naming the PR. An Epic's children are finished with it, so an Epic records one, on the Epic. The Notices module raises an `auto_merged` Notice from it (ADR 0042), naming the Ticket and linking the PR, so the User knows what reached the default branch while they were away. Approve merge and Merged raise none.
- **The completion rule checks the criteria.** The Tickets module's `completeTicket`, behind `finish_work` and Merged, refuses while any acceptance criterion is unchecked: the Ticket's own, and for an Epic the Epic's and every unarchived child's. The refusal names each unchecked criterion and its Ticket. Given an `override` reason, it completes and posts the reason as a comment by its actor, naming the unchecked criteria. A Ticket without criteria, or already Done, completes as before, so finishing again is harmless. It still checks nothing on GitHub.
- **Merged confirms instead.** The User's Merged button is never refused: when criteria are unchecked it lists them and asks the User to confirm, and a confirmed Merged completes with an override recorded as the User's comment.
- **One path to Done for Agents.** Agents finish all work with `finish_work`, PR or not: split specs, `ready-for-human` work and research too, so the triage state label is always removed. `update_ticket` with `status: Done` stays for the User's own edits.
- **Unchanged.** Autopilot never approves or starts a Merge. Approve merge and Merged stay. There is no Ticket-level label that forces the gate.

Rejected: Tandembike calling `gh pr merge` itself or checking GitHub in `finish_work` (ADR 0038's reasons stand); an Agent-set flag on `finish_work` saying it auto-merged (the Claim already knows the mode the run was given); and turning the setting into a repository instruction, as T1282 did, since the Playbook and the repository then told a run two things.

## Consequences

- With Autopilot and Auto-merge both on, a Cycle's ready work goes from Todo to merged and Done without the User; the run's own review, the Check command, the criteria and CI are the gate.
- Tandembike's own development keeps self-merging by having the Tandembike Project's Auto-merge on; its docs say "merge or hand off as `start_work`'s `merge` says".
- An Agent that leaves a criterion unmet must say why in `finish_work`'s `override`, which lands on the Ticket as a comment.
