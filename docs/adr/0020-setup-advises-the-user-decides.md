# Setup checks a repository against Tandembike's checklist; the User decides

Amended by [ADR 0032](0032-tandembike-ships-a-default-playbook.md): with the default Playbook, Setup only suggests extras and is not needed before a first run.

Amended by [ADR 0036](0036-mcp-calls-default-to-the-project-of-the-callers-folder.md): the checklist no longer asks for the Project's name in the instructions or for a per-repository MCP config.

Amended (T1556): Setup asks. It inspects the repository first, then goes through the checklist one item at a time, saying what it found and asking with its recommended answer: a Widget in the app (ADR 0045), the chat in a terminal. The checklist, still fixed in Tandembike's code, adds the Check command, `gh` installed and logged in, a CI workflow (without one Auto-merge always hands off), the default branch, an instructions file that says how to test, lint and run the app (a skeleton `CLAUDE.md` or `AGENTS.md` when it is missing or silent), a git guardrail hook offered as advice, and the first commit of a repository with none. It drops the worktree convention: since T1557 the runner makes each run's worktree on its branch (ADR 0033). Two exceptions to "advisory, edits only": Setup may save the Check command, with the MCP tool `set_check_command`, which refuses any run that is not Setup, and only on the User's yes; and it may make the first commit of a repository with none, on the User's Allow, since worktrees and Start runs need one. It still never pushes or opens a PR. On a re-run Setup compares instead of starting over, with the same brief: a Check command that matches its best suggestion is reported as kept with no question, one that differs is asked about once, naming both, and is never replaced or cleared without the User's yes; an existing instructions file gets only its missing sections as an edit, never the skeleton; an existing guardrail is "already present"; and any item that already matches gets one "already in place" line in the summary. It also reports each stored Agent command and whether the Playbook covers that Stage, so the User can clear it in Settings (report only: Setup never changes Agent commands), and searches the repository's instructions for a fixed list of outdated conventions, a branch pattern other than `ticket-<number>-<slug>`, agents told to make their own worktree or branch, `/to-spec`, `/to-tickets` or a local `/triage`, offering an edit for each. Setup is reachable from the CLI too: `tandembike setup` starts the same Conversation in the User's terminal, and `tandembike add` offers it after creating a Project.

ADR 0019 tells a run only its situation and leaves how to work to the repository. Runs still depend on a few things in that repository, and nothing there may say them: a `CLAUDE.md` that loads the repository's instructions, the Tandembike Project to use, the Tandembike MCP server for Agents the User starts in a terminal, an allowlist for the Tandembike tools, and, with Parallel runs on, a worktree convention. Setup is a Conversation in which an Agent checks the repository against that list and offers to add what is missing. For Setup only, Tandembike's brief says what to check. The list is fixed in Tandembike's code and covers only what Tandembike relies on, so branch names and the rest of the repository's process stay the repository's own.

Setup is advisory and the User decides. It does not gate agent mode or Start, and Tandembike stores no pass or fail result. Whether a repository is "set up" is the Agent's judgement, not something Tandembike can check, and the User may have reasons to differ. Every edit waits for the User's Allow. Setup works in the main checkout and never commits, pushes or opens a PR: the User reviews the diff and commits it their own way. Committing would need the very branch and worktree conventions Setup may be adding.

## Considered Options

- Gate agent mode until Setup passes: a "passed" flag would claim more certainty than an Agent's reading of a repository gives, and it would block a User who knows their repository is fine.
- Let the Agent judge freely what "ready" means: there is no stable list, and it drifts into the repository's own process, which ADR 0019 leaves alone.
- Report only, never edit: the User then makes every fix by hand, which is the friction Setup exists to remove.
- Commit through the repository's branch and PR rules: this fails exactly when those rules are what is missing.

## Consequences

- Setup does not count toward the Project's cap on concurrent Start runs, but a Project has at most one running Setup at a time, since two would edit the same files in one checkout.
- Projects that already held Setup are not asked to run it again when the checklist changes; the User reruns it from the Project's agent settings.
