# The server explains the tracker; each repository explains its process

Tandembike serves every repository on the machine, and its Agents may be Claude Code or GitHub Copilot. The rules for using the tracker (Statuses, Claims, acceptance criteria as a field, Blockers, Epics, Cycles, labels, reconnecting after tool changes) ship with the MCP server, in its instructions and tool descriptions, because that is the one thing every repository and every client already loads, and it cannot drift from the tools it describes. Each repository adds only what is its own: one line in `AGENTS.md` naming its Project, which both clients read, plus its process (branches, when a Ticket counts as done, triage roles), which the server deliberately leaves out. We rejected a doc copied into every repository, which goes stale, and a setup skill, which would work only in Claude Code. This repository's `docs/agents/issue-tracker.md` shrank to its own process accordingly (#63).

Clients cut long server text without warning: Claude Code keeps only the first 4,096 characters of the instructions and of each tool description, so rules at the end of the instructions never reached Agents (#106). The instructions therefore stay under a tested cap (`maxInstructionsLength` in `src/mcp/mcp-server.ts`, 3,500 characters) with the most important rules first. They say what to do and when; how a tool behaves, and any detail that concerns one tool, goes in that tool's description, and the instructions do not repeat it.

Tools that change a Ticket answer with its summary (number, title, Status, labels and whether it is blocked), plus the one field the call changed when the summary does not show it, such as `blockedBy` from `add_blocker` or only the named criteria from `set_acceptance_criteria_checked`. The Agent already holds what it just wrote, and echoing the whole Ticket spent its context on text it had: one Status change on a long spec sent the spec back in full (#131). `get_ticket` reads the whole Ticket, and `detail: "full"` on the tool itself returns it for a caller that wants it in the same call. The option is named `detail`, with the values `summary` and `full`, rather than `verbose`, because `list_tickets` already uses that name and those values for the same choice. The Tickets module's write functions still return whole Tickets, for the UI; the MCP tools turn them into summaries.
