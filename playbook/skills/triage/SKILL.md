Adapted from the `triage` skill of `mattpocock-skills` (MIT, see the plugin's LICENSE).

Triage the Ticket the first message names, such as `T42`, in the repository you are in. You only read and recommend: the User decides. Everything about the Ticket comes from the Tandembike tools; everything about the repository comes from its own instructions (`CLAUDE.md` or `AGENTS.md`, if it has them), its glossary and decision records, and its code.

## Roles

Two category roles, as labels: `bug` (something is broken) and `enhancement` (new feature or improvement).

Five state roles, as labels:

- `needs-triage`: the User needs to evaluate it.
- `needs-info`: waiting on the reporter for more information.
- `ready-for-agent`: fully specified, ready for an agent.
- `ready-for-human`: needs a human to implement it.
- `wontfix`: will not be actioned.

A triaged Ticket carries one category and one state. Move it between states with one `update_ticket` call that names the old state label in `removeLabels` and the new one in `addLabels`.

## Steps

1. **Read the Ticket.** Call `get_ticket` with the number: description, labels, acceptance criteria and every comment. Read earlier triage comments so you do not ask again what is answered. Use `find_tickets` to look for a duplicate or related Ticket.

2. **Check the codebase.** Learn the repository's domain language and decisions, then search for an existing implementation of the requested behaviour by domain concept, not only by the request's wording. For a bug, try to reproduce it from the reporter's steps. Note where you looked, whether or not you found anything.

3. **Recommend.** Post one comment with `add_note` that starts with this line, exactly:

   ```
   > *This was generated by AI during triage.*
   ```

   Then give:
   - the category and state you recommend, with your reasoning;
   - where you looked in the codebase and what you found, including whether the behaviour already exists (then `wontfix`, pointing to where it lives);
   - for `ready-for-agent` or `ready-for-human`, a short brief: the current behaviour, the desired behaviour, the interfaces involved, what is out of scope. Describe behaviour, not file paths or line numbers, which go stale. Acceptance criteria belong in the Ticket's acceptance criteria, not in the comment; when it has none, suggest them in the comment.

4. **Apply only what is yours to apply.**
   - Never apply `ready-for-agent` yourself, even when you recommend it: that is the User's call. Say in the comment that you recommend it.
   - You may apply `needs-info` (with `update_ticket`, replacing the old state label) when the Ticket cannot be judged without answers. Put the specific, answerable questions in the comment, under "What we still need". "Please provide more info" is not a question.
   - Leave every other state and the category for the User, unless the Ticket has no state at all: then apply `needs-triage`.

End your final message with one line: the category and state you recommend.

## When you cannot finish

Say what stopped you in a short comment with `add_note`, starting with the disclaimer, and end with that. Do not guess a recommendation you cannot support.
